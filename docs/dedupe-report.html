How tg-discovery recognises duplicates

How the service decides that something it finds is a venue or event it already knows, so that it is not reported as a new discovery. Describes the code as of 2026-10-18; the rules live in domain/fingerprint.py, pipelines/common/merge.py and store/repository.py.

Summary

Every venue and event gets an identity built from what identifies it in the real world: a Google place id, an OpenStreetMap id, its own website, its name and position, or, for an event, its title and venue. Two records with the same identity are the same thing. The service applies this at four levels: the request, the providers of one run, the runs over time, and (not built yet) TravelGay's own data. A record that matches one already stored is counted as changed or unchanged, never as new, and a candidate an admin has already approved or rejected is never put back in the review queue.

What already works: the same request is not searched twice within its TTL; the drafts several providers make of one venue or event within a run are merged into one candidate; a candidate found again in a later run with the same strongest key is recognised and updated instead of duplicated.
What does not yet: a later run only recognises a stored candidate by its single strongest key, with no fuzzy matching; and nothing is compared with what TravelGay already publishes. Section 6 lists the cases that slip through.

2. Identity rules

Name normalisation

Before names are compared they are normalised (normalize_name):

  • lower case; accents removed from Latin, Greek and Cyrillic letters (Sài Gòn → sai gon); Thai, Japanese, Korean and Chinese are kept as written;
  • & becomes and; punctuation is dropped;
  • generic words that say what a place is rather than which place it is are dropped: the, and, bar, club, pub, cafe, lounge, gay, lesbian, lgbt, queer, nightclub, sauna, spa, restaurant, hotel and a few more. The Heaven Gay Bar and HEAVEN both become heaven.

Event titles are reduced to a core title (core_title): years, edition and episode numbers are removed, so Pride Night 2026, Pride Night Vol. 3 and 5th Annual Pride Night all become pride night.

Venue keys, strongest first

Keys 3 to 5 carry the country and city, so same-name venues in different cities never merge. A website only counts when it is the venue's own: listings and social networks are not websites.

Event identity

  • Fingerprint (event_fingerprint): city + core title + venue (its Google place id, otherwise its normalised name, otherwise just the city). The date is not part of it: a weekly party is one candidate with many occurrences, not one per week.
  • Fuzzy rule (events_match): two events are the same when their core titles are at least 88 % alike (order of words ignored) and either they are at the same venue (same place id, within 150 m, or venue names at least 85 % alike) or their dates overlap.

3. Within a run: grouping and merging drafts

Each provider turns what it found into drafts. For each city, the drafts are grouped with a union-find: if A matches B and B matches C, all three are one group.

  • Venues (group_venues): two drafts are one venue when any of their keys match. A draft without coordinates also joins drafts with exactly the same normalised name.
  • Events (group_events): same fingerprint, or the fuzzy rule between any two drafts.

Each group becomes one candidate (merge_venue, merge_event): the most complete draft is the base and its gaps are filled from the others; nothing is invented. Conflicts are settled by rule:

FieldRule
Most fields (address, phone, website, price, organiser…)first value found, most complete draft first

Example: Google Maps finds Heaven with a place id and its website; Exa finds a guide that names The Heaven Gay Bar with the same website. They share the website key, so the reviewer sees one candidate, found by two providers, with the place id from Maps and the description from the guide. A candidate found by two or more providers also scores higher on source trust and verifiability.

4. Across runs: is it really new?

When a run saves its candidates (save_candidates), each candidate is looked up by its fingerprint (its strongest key; a unique column in the candidate tables):

fingerprint not stored yet          → insert                    outcome: new
fingerprint stored, content differs → update the candidate      outcome: changed
fingerprint stored, content same    → keep it; only fill details
                                      that were empty (phone,
                                      hours, organiser contacts,
                                      pictures)                 outcome: unchanged
stored candidate already approved
or rejected                         → never reopened; the
                                      admin's decision stands

"Content" is a hash of the material fields (venue_content_hash, event_content_hash): for a venue its name, address, rounded position, website and status; for an event its core title, dates and times, venue and official link, and status. A reworded description does not count as a change. Every time a candidate is found, a sighting row records the run, the outcome, the providers and the score.

This is how the service knows that something is not a new discovery: only new means first seen; a rejected candidate stays rejected however often it is found again.

6. Known gaps: how a duplicate can still get through

  1. Across runs only the strongest key is compared. Within a run any shared key merges two drafts, but the stored fingerprint is a single key. If Heaven was stored with its Google place id and a later run finds it only through Exa, the new draft's strongest key is its website, so it is stored as a second candidate.
  2. No fuzzy matching across runs. The event fuzzy rule runs only inside one run. Titles written differently on different days (Oï Oï Oï and O ï O ï O ï), or a venue named with and without its district (Clutch and Clutch, Talat Noi), give different fingerprints and become two candidates when they are found by different runs.
  3. Venue names are only compared exactly. There is no fuzzy rule for venues: Saigon and Sai Gon, a name in Thai script and its English name, or Heaven and Heaven Bangkok do not match by name; they merge only when an id, a website or a 150 m cell is shared.
  4. Venues without coordinates merge only with exactly the same normalised name.
  5. Nothing is compared with TravelGay. A venue or event already published on TravelGay can be proposed as new.
  6. The event fuzzy rule compares every pair within a city, so it slows down as a run finds more events (about 8 seconds for 750 drafts in a test).

7. Improvements, in order

#ChangeFixes gap
1Store every identity key of a candidate in a candidate_keys table and look up a new draft by any of its keys, as the in-run grouping already does.1
2Fuzzy check against stored candidates of the same city: for events, the fuzzy rule over candidates whose dates are near; for venues, a name similarity of at least 90 % within 200 m.2, 3
3Better normalisation: compare names without spaces and punctuation; drop a trailing district or city after a comma in venue names; transliterate non-Latin scripts for the comparison only.2, 3
4Known set: read TravelGay's venues and events (read only) and match them by website, name and position (TravelGay venues and hotels carry coordinates), filling dedupe.tg_match.5
5"Possible duplicates" for the reviewer: fill dedupe.similar with near matches below the merge threshold, and add an admin action to merge two candidates.all, as a safety net
6Faster event matching: compare only events with the same first title word or within a date window, instead of every pair.6

8. How to measure dedupe quality

  • Duplicate rate: candidates rejected with reason duplicate divided by all decided candidates, per run and per city. Rising means duplicates are getting through.
  • Labelled pairs: sample pairs of candidates of one city that the rules did not merge but that look alike, and pairs they did merge; an admin labels each pair "same" or "different". From these, precision (merged pairs that were really the same) and recall (same pairs that were merged) show whether the thresholds (88 % titles, 85 % venue names, 150 m) should move.
  • Regression tests: each duplicate found in review becomes a unit test of the identity rules, so a fix never comes undone.
